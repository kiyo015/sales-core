# 業務ルールを変えるときの手順

業務ルールは `docs/domain/business-rules.md` が唯一の定義元。コード・テスト・文書の3つが同じ決まりを表していなければならない。1つだけ直すと、次に読んだ人(とClaude)がどれを信じればよいか分からなくなり、請求額の誤りにつながる。

## 1. 変える決まりを特定し、本人に確かめる

- `business-rules.md` の該当する節を読み、**今の決まり・決めた日・理由**を確かめる
- 業務の決まりを決めるのは本人。依頼があいまいなとき、または決まりの意味が変わるとき(例: 「切り捨て」が明細ごとか請求書ごとか)は、`AskUserQuestion` で選択肢を出して決めてもらう。推測で決めない
- 変えると影響が出る範囲を挙げる: 過去の伝票(確定済みの請求書は変えない)、税率の期間、赤伝との打ち消し

## 2. 文書を先に直す

- `business-rules.md`: 新しい決まり、**変更日**、理由。古い決まりを消すときは「YYYY-MM-DD まではこうだった」を残す(過去の請求書の説明に要る)
- 影響があれば `glossary.md`・`business-flow.md`・`er-diagram.md` も
- `CLAUDE.md` の禁止事項の表に関わるなら、そこも

## 3. テストを先に変え、狙った理由で落ちることを見る

| 決まり | テストの場所 |
|---|---|
| 金額・端数処理 | `tests/SalesCore.Domain.Tests/MoneyTests.cs` |
| 消費税 | `TaxCalculatorTests.cs` |
| 受注・出荷・返品の状態と金額 | `SalesOrderTests.cs`・`SalesRecordTests.cs` |
| 請求 | `InvoiceTests.cs` |

- 新しい決まりの例を足す。**古い実装と新しい実装で結果が変わる値**を必ず入れる(どちらでも同じ答えになる例だけでは、変更を確かめられない)
- ランダムテストの期待値は、製品コードと別の方法(`long` の整数計算など)で出す
- テストを走らせ、**古い実装のまま、狙ったテストが狙った理由で落ちる**ことを確かめる

## 4. 実装を直す(決まりは1か所にしか無い)

| 決まり | 実装の場所 |
|---|---|
| 端数処理 | `Money.Round` だけ(他の場所で丸めるとビルドが RS0030 で落ちる) |
| 税額 | `TaxRate.TaxOn`・`TaxCalculator.Calculate` |
| 受注の状態 | `SalesOrder`(状態ごとの検査) |
| 分納・返品の金額 | `SalesOrderLine`(累計差分) |

ビルドが RS0030・SALES001・SALES002 で落ちたら、抑止せずに `Money` を使って書き直す。

## 5. 古い決まりの残りを探す

古い値や言い回しで検索し、コード・テスト・文書・`CLAUDE.md` に残っていないかを確かめる(例: 税率なら `10m`・`10%`、丸めなら `AwayFromZero`・「四捨五入」)。見つかったものは、直すか、残す理由を書く。

## 6. 確かめる

- `dotnet build` と `dotnet test` がすべて成功する
- **対照実験**: 古い実装に一時的に戻すと、手順3のテストが落ちる
- `team-reviewer` で差分をレビューする。渡すのは `git diff` と「どの決まりを、なぜ変えたか」

## 7. 記録する

コミットメッセージに、変えた決まり・本人が決めた日・確かめたこと(落ちたテストの件数など)を書く。
