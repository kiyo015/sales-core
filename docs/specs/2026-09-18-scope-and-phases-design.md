# 機能範囲と段階構成の設計（2026-09-18）

販売・購買・請求の基幹システム`sales-core`の機能範囲を広げ、5つの段階に分けて開発する。

## 背景

当初の計画は「受注 → 出荷 → 請求書発行」の縦切り1本（20日）だった。販売・購買・在庫・画面・権限・帳票・外部連携までを範囲に含めることにし、期間を延ばして段階的に作る。

## 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| 範囲 | 販売の完結、購買と在庫、画面と権限、帳票と外部連携をすべて含める | 基幹システムとして一通りの業務を扱うため |
| 進め方 | 段階に分けて期間を延ばす（平日約78日） | 1か月に詰めると、金額や状態遷移の「強制」とテストが薄くなり、後で作り直しになる |
| 段階の順番 | 画面と権限 → 販売の完結 → 購買と在庫 → 帳票と外部連携 | 早い段階から画面で触って確かめられるようにする |
| 画面の技術 | Blazor Web App（.NET 8） | C#だけで完結し、APIと型を共有できる。ひとりで作るなら言語が1つで済む |
| ログイン | ASP.NET Core Identity | ユーザーはこのシステムのDBで管理する |

テーブル構造は`docs/domain/er-diagram.md`（同日作成）。業務上の決定（締め請求＋請求先の分離、分納あり、複数倉庫、得意先別単価あり）はそちらに記録している。

## 段階の構成

| 段階 | Day | 日数 | 内容 | 終わった時点で動くもの |
|---|---|---|---|---|
| 1 | 15〜34 | 20 | 基盤と縦切り | APIで受注 → 出荷（分納あり） → **締め請求書の発行** |
| 2 | 35〜49 | 15 | 画面と権限 | ログインし、役割に応じた画面で受注〜請求を操作できる |
| 3 | 50〜63 | 14 | 販売の完結 | 見積から入金・消込まで。売掛金の残高が出る |
| 4 | 64〜79 | 16 | 購買と在庫 | 発注から支払まで。在庫が無ければ出荷できない |
| 5 | 80〜92 | 13 | 帳票と外部連携 | 請求書などのPDF、会計ソフト向けの仕訳、銀行入金の取り込み |

### 段階1の変更点（当初の20日計画から）

- 縦切りのゴールを「請求書の発行」から**「締め請求書の発行」**に上げる（請求方式を締め請求と決めたため）
- 得意先には最初から**請求先と締め日**を持たせる。後から足すと得意先の構造を作り直すことになる
- 分納を最初から扱う（受注明細に出荷済み数量を持つ）
- 倉庫マスタは1件だけ登録して使う（出荷が倉庫を参照するため）。複数倉庫での在庫の移動は段階4
- 得意先別単価は段階3。段階1の受注は商品の標準単価を使う

### 段階2「画面と権限」

- `src/SalesCore.Web`にBlazor Web Appとして作る。**画面は薄く保つ**。業務の判断はAPIとDomainに置き、画面は表示と入力だけを担う（業務ルールが増えても画面の手直しが増えないようにするため）
- ASP.NET Core Identity。パスワードの規則・失敗回数によるロック・ハッシュ化は標準機能を使い、自作しない
- 役割は営業・経理・管理者の3つ。APIごとに呼べる役割を認可のポリシーで決め、監査ログに操作した人を記録する
- 一定金額以上の受注は、管理者が承認するまで出荷できない（基準額は業務ルール集で決める）
- 画面：マスタ（得意先・商品・倉庫）、受注・出荷・締め請求（明細の入力を含む）
- テスト：部品単位はbUnit、画面を端から端まで通すのはPlaywright
- 権限の実効性テスト：「営業が経理のAPIを呼ぶと拒否される」ことを、権限を外した場合と比べて確かめる

### 段階3〜5

範囲はER図の各領域のとおり。**日単位の計画は各段階の最初に作る。** 業務ルールは作りながら固まるので、先に全部を決めると古くなる。

- 段階3：見積、得意先別単価、入金・消込、売掛金残高、月次締め
- 段階4：仕入先・仕入単価、発注 → 入荷・検収 → 仕入 → 支払・買掛金、在庫（引当・入出庫・棚卸）
- 段階5：PDF（請求書・納品書・発注書）、会計ソフト向けの仕訳データ、銀行入金データの取り込みと自動消込

## やらないこと（この計画の範囲外）

- 本番環境へのデプロイと運用監視（全段階の完了後に別途計画する）
- 社内アカウント連携（Microsoft Entra IDなど）。Identityで始め、必要になったら差し替える
- 多通貨・多言語

## 進め方の約束

- 各段階の最終日は振り返りにあて、次の段階の日単位の計画を作る
- 段階ごとに作るのは、その段階で使う表だけ
- 新しいガード（権限・禁止事項）を入れたら、その段階のうちに実効性テストを書く
