# 業務フロー

用語は`glossary.md`、判断の決まりは`business-rules.md`に従う。図の中の括弧は段階（どの段階で作るか）。段階1（API）と段階2（画面・ログイン・権限・承認）の部分は作ってある（2026-11-11）。誰がどの操作をするかは「5. 誰が操作するか」。

## 1. 販売の流れ（受注から入金まで）

```mermaid
flowchart TD
    A["見積を出す<br/>(段階3)"] -->|受注になる| B["受注を登録する<br/>(段階1)"]
    B --> C{"税抜合計<br/>100万円以上?"}
    C -->|はい| D["管理者が承認する<br/>(段階2)"]
    C -->|いいえ| E["在庫を引き当てる<br/>(段階4)"]
    D --> E
    E --> F{"在庫は足りるか"}
    F -->|足りる| G["出荷を指示する<br/>(段階1)"]
    F -->|足りない| H["入荷を待つ<br/>(段階4)"]
    H --> E
    G --> I["出荷を確定する<br/>= 売上計上<br/>(段階1)"]
    I --> J{"受注は<br/>すべて出荷したか"}
    J -->|残りあり| G
    J -->|完了| K["締め日に請求書を作る<br/>(段階1)"]
    K --> L["請求書を発行する<br/>PDF (段階5)"]
    L --> M["入金を登録する<br/>(段階3)"]
    M --> N["請求と消し込む<br/>(段階3)"]
    N --> O["売掛金の残高が減る<br/>(段階3)"]
```

**分納**: 「出荷を確定する」から「受注はすべて出荷したか」で残りがあれば、再び出荷指示に戻る。受注明細の出荷済み数量で判定する。

## 2. 購買の流れ（発注から支払まで・段階4）

```mermaid
flowchart TD
    A["発注する"] --> B["入荷する"]
    B --> C["検収する<br/>(合格数を決める)"]
    C --> D["仕入を計上する<br/>(合格数のみ)"]
    C --> E["在庫が増える"]
    D --> F["仕入先の請求書を受け取る"]
    F --> G{"自社の仕入計上と<br/>一致するか"}
    G -->|一致する| H["支払う"]
    G -->|一致しない| I["仕入先に問い合わせる"]
    I --> F
    H --> J["買掛金の残高が減る"]
```

## 3. 受注の状態（段階1・承認は段階2）

```mermaid
stateDiagram-v2
    [*] --> 受付: 税抜100万円未満で登録
    [*] --> 承認待ち: 税抜100万円以上で登録
    受付 --> 承認済: 営業か管理者が承認
    承認待ち --> 承認済: 管理者が承認
    承認待ち --> 取消: 却下・取りやめ
    承認済 --> 一部出荷: 一部を出荷確定
    承認済 --> 出荷済: 全量を出荷確定
    一部出荷 --> 一部出荷: 残りの一部を出荷
    一部出荷 --> 出荷済: 残り全部を出荷
    受付 --> 取消
    承認済 --> 取消: 未出荷のときだけ
    出荷済 --> [*]
    取消 --> [*]
```

**出荷済みの受注は取り消せない。** 出荷後に誤りが見つかった場合は、赤伝で打ち消す（`business-rules.md`の「締めた後に誤りが見つかったら」）。

**返品しても状態は戻らない。** 返品は負の売上として計上し、受注の状態と出荷済み数量はそのまま（`business-rules.md`の「返品」）。状態ごとにできる操作の表は`business-rules.md`の「状態」にある。

承認待ちは 2026-10-29（段階2）に足した。登録した時の税抜合計で、受付か承認待ちのどちらで始まるかが決まる（本人の決定。100万円は設定の既定値。`business-rules.md`の「承認」）。それまでのコードでは、受付から金額を問わず承認済へ進んでいた。

### 出荷の状態（段階1）

```mermaid
stateDiagram-v2
    [*] --> 指示: 受注から出荷を指示
    指示 --> 確定: 出荷を確定 = 売上計上
    指示 --> 取消
    確定 --> [*]
    取消 --> [*]
```

受注の出荷済み数量と状態が動くのは、出荷を確定したときだけ。確定した出荷は取り消せない（打ち消すのは返品）。

## 4. 締めと請求（段階1）

```mermaid
flowchart LR
    A["得意先ごとの締め日<br/>(5/10/15/20/25/月末)"] --> B["前回締め日の翌日から<br/>今回締め日までの売上を集める"]
    B --> C["税率ごとに集計し<br/>税額を1回だけ四捨五入"]
    C --> D["前回請求額 − 入金額<br/>= 繰越"]
    D --> E["請求額 = 繰越 + 今回売上 + 税額"]
    E --> F["請求書を確定<br/>(売上に請求書番号が入る)"]
```

**締め済みの売上は二重に請求しない。** 売上に請求書の参照が入っているかどうかで判定する。

## 5. 誰が操作するか（段階2）

役割ごとにできる操作の唯一の定義元は `business-rules.md` の「役割」の表。ここでは、段階2で作った画面の流れに、誰が手を動かすかを重ねる（管理者はどの操作もできるので省く）。

```mermaid
flowchart LR
    A["営業: 受注を登録する<br/>(受注の画面)"] --> B{"税抜合計<br/>100万円以上?"}
    B -->|いいえ| C["営業: 承認する"]
    B -->|はい| D["管理者: 承認する"]
    C --> E["営業: 出荷を指示・確定する<br/>(受注の詳細から)"]
    D --> E
    E --> F["経理: 締めて請求書を作る<br/>(締め請求の画面)"]
    G["管理者: 得意先・商品・倉庫を登録する<br/>(マスタの画面)"] -.-> A
```

- **ログインしていなければ、どの画面も使えない。** 役割の無い操作のボタンやリンクは出ず、URL を直接開いても 403 の理由が出る（守りはユースケースの入口の検査）。
- **役割を外したり利用者を無効にしたりすると、画面では1分以内に効く**（`business-rules.md`「8.」）。API のトークンは期限の1時間まで通る。
- 利用者を作る・役割を変える画面はまだ無い。初期の利用者は各自の user-secrets から作る（`CLAUDE.md` の「DBの準備」の4）。
